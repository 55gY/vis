# WWFilter — 全新透明加密 minifilter 驱动（设计）

全新实现，完全不依赖旧客户端的 DLL / 驱动。只按旧客户端现有的
策略与加密逻辑重写：S-box 流密码、512 字节头、.xcf 策略语义。
目标：Win 全兼容、透明、兼容旧客户端加密格式、去掉许可证与装机数验证。

## 1. 架构

```
应用 (notepad.exe 等)
   |  NtReadFile / NtWriteFile / CreateFile ...
   v
Windows 缓存管理器 (缓存里放明文)
   |  分页 I/O (刷盘 / 换入) 与非缓存 I/O
   v
WWFilter (minifilter, 内核)  <--- 本驱动：只在分页/非缓存 I/O 层加解密
   |  IRP_MJ_CREATE / READ / WRITE / SET_INFORMATION / QUERY_INFORMATION
   v
文件系统 (NTFS) -> 磁盘 (文件 = [512 字节头][密文])
```

- **不注入进程，不 hook user 态 API。** 驱动挂在文件系统下面，
  所有进程的读写都经过它。没有“某个进程没注上就不加密”的问题。
- **加密只在分页 I/O 与非缓存 I/O 层发生**（IRP_PAGING_IO 或
  IRP_NOCACHE）。缓存 I/O 不碰（缓存里是明文）。这是防重复加密
  的铁律：同一份数据只加密一次。
- **引擎就是驱动本身。** 没有独立的引擎 DLL。S-box 密码、策略判定、
  头处理、偏移换算全在驱动里做。

## 2. 文件格式（与旧客户端一致，保证互通）

- 磁盘文件 = `[512 字节头][密文]`；应用看到的逻辑文件 = N 字节明文。
- 头（512 字节）：
  - +0x00：16 字节 magic `40 21 28 15 2a 2d 1b 20 23 30 1e 19 2f 22 16 40`
  - +0x10：u16 version（2 → 表 B；1 → 表 A）
  - +0x12：策略名（ASCII，如 `NOTEPAD.`；新文件写进程名大写 + `.`）
  - +0x30..0x4f：32 字节密钥（每文件随机，头里明文存放）
  - 头 +0x12..0x1ff 以计数器从 0 起加密（与旧逻辑一致）
- 密码（S-box 流密码，见 `sbox_tables.h` 与 `sbox.c`）：
  - 基础表 A（version 1）或 B（version 2），再用 32 字节密钥做
    16 次换位 `S[key[i]] <-> S[key[i+16]]`（i=0..15）得到 keyed S-box，
    再求逆表。
  - `cipher[i] = S[plain[i]] + addend(counter)`，
    `addend(counter) = (counter & 0xff) | ((counter >> 8) & 0xff)`，
    计数器逐字节 +1。
  - 解密：`plain[i] = invS[(cipher[i] - addend(counter)) & 0xff]`。
  - **计数器 = 明文文件偏移。** 逻辑偏移 X 处的字节用计数器 X。
    所以随机读写、局部写、多线程写不同偏移都是安全的
    （每字节只取决于自己的偏移）。
- **头永不加密。** 数据写永远从物理偏移 512 开始。头只写一次。

## 3. 策略模型（与 .xcf 一致，不是只看扩展名）

策略按**进程**来，一个文件加不加密同时看：

- `Encrypt <程序> = Write / Read`：该程序保存时加不加密。
  Write 才加密；Read 只解密、不加密。
- `File <程序> = <扩展名列表>`：该程序管哪些类型。
  如 `File notepad.exe = txt|pdf`。
- `dir / wild / include`：按路径匹配的规则（逐进程）。

判定流程（在 IRP_MJ_CREATE 时做一次，结论缓存进流上下文）：

1. 取请求进程的 exe 名，查策略表。没有 Encrypt 规则 → 不加密，
   不挂上下文，直接放行。
2. 有 Encrypt 规则：扩展名对不上该进程的 File 列表 → 不加密。
3. 路径对不上 dir/wild/include → 不加密。
4. 全对上：
   - Encrypt == Write：该文件要加密。已有头 → 用头里的密钥；
     新文件 → 生成随机密钥、写头。
   - Encrypt == Read：只读解密（有头才解密），写不加密。
5. 结论（加密/不加密、读写模式、密钥/S-box）存在**流上下文**里。
   之后每次读写只查上下文，不重新算策略。

**快路径**：扩展名先对 File 列表做一次粗筛（大多数文件不在
策略里）；不加密的文件在 pre-op 返回
`FLT_PREOP_SUCCESS_NO_CALLBACK`，连 post-op 回调都省了。

## 4. I/O 回调与偏移换算

| 回调 | 做法 |
|---|---|
| CREATE pre-op | 按 §3 判定策略；要加密则挂流上下文，返回 WITH_CALLBACK |
| CREATE post-op | 新文件（FILE_CREATED）且 Encrypt==Write → 写 512 字节头；已有文件 → 读头取密钥（magic 不对 = 明文文件，见 §5） |
| READ pre-op | 只对分页/非缓存读：把 ByteOffset += 512，返回 WITH_CALLBACK；缓存读直接放行 |
| READ post-op | 分页/非缓存读成功后解密 buffer（计数器 = 逻辑偏移） |
| WRITE pre-op | 只对分页/非缓存写：在 buffer 里加密（计数器 = 逻辑偏移），ByteOffset += 512；缓存写直接放行（进缓存是明文，刷盘时再加密） |
| SET_INFORMATION pre-op | FileEndOfFileInformation / FileAllocationInformation：大小 += 512 |
| QUERY_INFORMATION post-op | FileStandardInformation 等：EndOfFile / AllocationSize -= 512（报逻辑大小） |
| CLEANUP / CLOSE | 流上下文由 Filter Manager 在流销毁时经清理回调释放 |

**铁律**：

- 偏移换算只对分页/非缓存 I/O 做。缓存 I/O 的偏移是逻辑偏移，
  缓存按逻辑偏移索引，绝不能加 512。
- 头（物理 0..511）永不加密，数据写永远从物理 512 开始。
- 状态不一致（上下文丢了、偏移算不出来）→ 让这次 I/O 失败，
  不继续写。写失败应用能看到报错，比悄悄写坏文件强。

## 5. 驱动内数据结构

- **流上下文**（每文件流一份，随流创建分配、流销毁释放）：
  `is_encrypted`、`mode`（Write/Read）、`key[32]`、`sbox[256]`、
  `inv_sbox[256]`、`policy_name`、`header_written`、一把锁。
  内存正比于**同时打开**的加密文件数（每份约 1KB），不随历史
  打开总数增长。
- **策略表**（驱动里一份，由服务经 IOCTL 下发）：
  活动策略组名 + 进程规则表（exe 名 → Encrypt 模式 + File 扩展名
  列表 + dir/wild/include 规则）。更新时原子替换（写时复制 +
  指针交换，读侧无锁或用 ERESOURCE 共享锁），保证一次 I/O
  只看到旧表或新表，不会混用。
- **换页 buffer**：用 lookaside list 分配，用完即还。
- **事件环**（加解密日志，见 §7）：固定大小环形缓冲（默认 4096 条），
  满了覆盖最旧的，不无限增长。

## 6. IOCTL 接口（控制设备 `\\Device\\WWFilter`，服务经此与驱动对话）

| IOCTL | 方向 | 说明 |
|---|---|---|
| `IOCTL_WWFLT_SET_POLICY` | 服务 → 驱动 | 下发/替换整张策略表（§5 的序列化格式）。服务从本地 .xcf 读，或以后从服务端拉取后下发。驱动原子替换。 |
| `IOCTL_WWFLT_GET_STATUS` | 驱动 → 服务 | 状态：已打开加密文件数、累计加密/解密字节、策略判定次数、错误计数、驱动版本。 |
| `IOCTL_WWFLT_GET_EVENTS` | 驱动 → 服务 | 取事件环（加解密日志）里未读的条目。服务读出后写日志文件 / 上报服务端。 |
| `IOCTL_WWFLT_SET_LOG_LEVEL` | 服务 → 驱动 | 日志详细程度（0=只记错误，1=记加解密事件，2=记策略判定）。 |
| `IOCTL_WWFLT_SET_CONFIG` | 服务 → 驱动 | 其他开关（预留：如是否启用、调试标志）。 |

IOCTL 统一用 `METHOD_BUFFERED`，结构体定义见 `wwflt.h`
（驱动与服务共用同一份头文件）。

## 7. 预留接口（本期只定接口、留位置，不全做）

### 7.1 策略更新接口（服务端 → 服务 → 驱动）

- **传输层**：服务负责，wss / TCP / HTTP 都可以，本期先定
  “服务拉取、驱动只收 IOCTL”的分工。驱动不做任何网络。
- **流程**：服务端下发策略（.xcf 或等价 JSON）→ 服务收到后
  解析 → 经 `IOCTL_WWFLT_SET_POLICY` 推给驱动 → 驱动原子替换。
  服务本地 .xcf 是回退（断网时用本地策略）。
- **预留**：策略表里加 `version` / `rev` 字段，服务端下发带
  版本号，驱动拒绝旧版本覆盖新版本（防乱序）。

### 7.2 管理策略接口 / GUI

- GUI 不直接碰驱动。GUI ↔ 服务（本地 IPC：命名管道或
  localhost HTTP），服务 ↔ 驱动（IOCTL）。
- GUI 能做的事（经服务）：查看当前策略、编辑策略（改完经服务
  下发到驱动）、查看状态（`GET_STATUS`）、查看日志
  （`GET_EVENTS`）、开关驱动。
- 本期服务先实现“读本地 .xcf → 下发驱动”这一条通路，
  GUI 的 IPC 接口位置先留好（服务内一个 `mgmt` 模块）。

### 7.3 加解密日志

- 驱动内事件环：每条 = 时间戳、进程名、文件路径、操作
  （创建/读/写/加密/解密）、结果（成功/失败 + 错误码）、
  字节数。只记“做了什么”，不记文件内容。
- 服务定时（或按条数）经 `GET_EVENTS` 读出，写本地日志文件
  （`wwflt.log`），并（以后）批量上报服务端。
- 日志级别可调（`SET_LOG_LEVEL`），默认记加解密事件，不记
  每次策略判定（太吵）。

### 7.4 服务端

- 只做两件事：**下发策略**、**收集日志**。不做许可证、不统计
  装机数、不设上限、不复刻旧服务端。
- 客户端分独立模式（只用本地 .xcf）与服务端模式（连服务端
  拉策略、上报日志）。本期先做独立模式，服务端模式留接口。
- 传输建议 HTTPS（复用现有 VPS + nginx），认证与策略格式
  （.xcf 下发）待定，不阻塞本期。

### 7.5 其他预留（用户说“或许还有我没考虑到的”）

- **卸载/回滚**：驱动提供 `IOCTL_WWFLT_SET_CONFIG` 的停用开关；
  服务卸载时先停驱动、再删服务。万一新驱动出问题，停用后
  文件保持加密状态（磁盘上的密文不受影响），旧文件仍可用
  Python 解密脚本离线解密。
- **兼容旧文件**：按 §2 的格式，旧客户端加密的文件新驱动
  能直接读（同 magic、同 S-box、同计数器规则）。新驱动加密的
  文件，旧客户端也能读（格式一致）。
- **多卷**：实例装到所有固定卷；可移动卷（U盘）默认不装，
  由策略的 usb 开关以后控制。
- **WOW64 / 32 位进程**：minifilter 在内核层，不分 32/64 位
  进程，天然全覆盖。

## 8. 构建与测试

- **构建**：WDK（Windows Driver Kit）+ Visual Studio，在 Windows
  上编。Linux 下编不了内核驱动。本仓库只放源码与工程文件。
  目标：Win10 x64（测试机）；Win7/Win11 兼容以后再测。
- **签名**：开发期用测试签名（`bcdedit /set testsigning on` +
  关安全启动 + 重启）。正式发布再走 EV + 微软签名。
- **测试环境**：PVE 虚拟机（Win10 专业版），测前打快照。
  **先用文件副本测，不碰真实文件。**
- **验收（Phase 1）**：
  1. 驱动加载成功（testsigning 模式），服务能下发策略。
  2. 记事本新建 .txt、保存 → 磁盘文件有 512 字节头 + 密文，
     Python 解密脚本能解回明文。
  3. 重新打开该文件 → 记事本看到明文。
  4. 压力：循环开/关 1 万个文件，驱动池用量回到基线
     （不漏内存）。
  5. 正确性：写已知数据（多种大小、随机 seek 写、局部写），
     读回逐字节比对；多进程同时写不同文件。
- **已知 Phase 1 局限**（下一期再做）：
  - 已存在的明文文件被 Write 策略进程打开并写入时，本期
    **不做整文件转换**（只加密新创建的文件）。要测加密请用
    新建文件。
  - dir/wild/include 路径规则本期只做基本通配符（`*`/`?`），
    复杂规则以后补。
  - 32 位 Windows 本期不做（只做 x64）。
